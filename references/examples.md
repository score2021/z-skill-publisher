# 把原则写成可执行判断

当规则仍抽象、例外难写或不确定该用什么结构时读取。以下是合成写作示例，未经模型对照验证，不是必须逐字套用的模板，也不是生成物 README 的实际成果展示。

## 1. 从形容词到可观察行为

原写法：

> 你是专业的汇报专家，输出清晰、准确、有洞察力的周报。

可改为：

> 按目标汇总本周发生的变化，给每个结论标出输入依据。已完成、进行中和计划分开；输入未给进度比例就不编百分比。跨周材料先核对日期，无法判断的条目标为待确认。

原因：具体约束会改变分类与事实判断。输入“准备发布”应进入计划或进行中；输入“已于周二上线”才支持完成。角色称谓不能解决这个区别。

## 2. 从一次失败到条件处理

原写法：

> 命令超时后固定等待 30 秒，使用 Python 重写，再重试三次。

可改为：

> 先区分无输出的长任务、明确超时和输入错误。仍在运行的任务继续读取状态；输入错误先修正输入；确认属于可恢复的临时服务故障时，在已有权限内有限重试并设停止条件。不能靠重写语言解决权限或服务不可用。

原因：长任务不应重复启动，错误输入不应等待，权限不足不应绕过。只有稳定、相关的故障分支值得保留；某次成功用了 Python 不足以把它设为通用要求。具体重试上限按服务与任务风险确定。

## 3. 默认、硬约束与例外

原写法：

> 所有导出都必须用 CSV。

若来源只是用户偏好，可改为：

> 用户未指定格式时默认 CSV，便于下游表格工具处理；需要多表或保留格式时，说明 CSV 的限制并按需求选择其他支持格式。

若来源是接口只支持 CSV，应写：

> 该接口仅接受 CSV。收到 XLSX 时先转换并核对类型与编码；无法可靠转换则报告限制，不上传不兼容文件。

原因：同一动作可能来自偏好或能力限制，二者的例外不同。验证应分别覆盖未指定格式、明确要求其他格式及接口不支持的输入。

## 4. 按任务选择输出

原写法：

> 每次输出背景、问题、分析、计划、风险、结论六章。

可改为：

> 术语查询直接给术语和一句解释，歧义时列最接近的区别；诊断给证据、原因和验证方法；构建交实际产物与必要使用说明。只有需要决策或交接时才展开报告。

原因：结构应让下一步更容易。问“这个效果叫什么”无需六章；要交接修复任务则需要位置、具体修改与完成标准。

## 5. 修复模式和示例的冲突

原写法：

> 本 skill 永远只读。`fix` 模式自动修复全部问题。

可改为：

> 评估模式只读取指定材料并提交建议；明确要求实施时才修改选定范围，复验结果。若用户一开始已要求“检查并修复”，在该范围内连续完成，不再机械等待确认。

原因：边界按模式和当前授权确定。评估请求不应写文件；已授权修复也不应被全局只读禁令卡住。样例和测试必须体现同一边界。

## 6. 精简与按需读取

原写法：

> 为每个 skill 建立脚本目录、十类参考文档，并在开始时全部读取。

可改为：

> 先写完成任务所需的最小指令。仅在某种场景需要精确 API 时读 API 参考；只为稳定重复操作增加脚本。简单术语查询可以只有 SKILL.md。

原因：资源应减少重复劳动或避免错误。不能用目录齐全代替实际能力，也不能让普通任务加载所有低频细节。
